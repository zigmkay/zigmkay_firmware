# zkeycodes

A Zig code generator that converts QMK keyboard layout definitions (HJSON format) into Zig source files. The generated files are usable as a library (`zkeycodes`) in Zig keyboard firmware projects.

## What it does

QMK maintains keyboard layout definitions in HJSON files. Each file defines either:

- **Basic keycodes** (`*_basic.hjson`): the raw HID keycode table, grouped by category (basic, modifiers, media, mouse, etc.)
- **Locale layouts** (all other `.hjson` files): a mapping from locale-specific names (e.g. `DE_A`, `DE_EXLM`) to base keycodes or modifier+keycode combinations (e.g. `S(DE_1)` for `!` on a German layout)

The generator reads these files and produces `.zig` source files with typed constants and a `getLabel` function for runtime label lookup.

## Project structure

```
zkeycodes/
├── src/
│   ├── main.zig        # Code generator (the executable)
│   └── core.zig        # Shared types: LabelEntry, Modifiers, modifier functions (S, A, ALGR)
├── keycodes/           # Generated Zig files (checked in, regenerated by `zig build test`)
│   ├── keycodes.zig        # Basic HID keycode table
│   ├── german.zig          # German (DE) layout
│   ├── german_mac_iso.zig  # German Mac ISO layout
│   ├── us_international.zig
│   └── danish.zig
├── input/              # Drop HJSON files here for batch conversion (see `zig build convert-all`)
├── test_data/          # Input HJSON files used by the test suite
│   ├── keycodes_0.0.1_basic.hjson
│   ├── keycodes_german_mac_iso_0.0.1.hjson
│   └── … (one file per layout)
├── root.zig            # Module entry point — re-exports all generated layouts
├── build.zig
├── test_generation.zig # Tests that verify generated code compiles and evaluates correctly
└── test_labels.zig     # Tests for the getLabel function
```

## Building

Requires Zig 0.17.0 or later.

```sh
zig build          # builds the generator executable
zig build test     # regenerates keycodes/ from test_data/ and runs all tests
```

The `test` step regenerates all files in `keycodes/` before running tests, so the checked-in files are always up to date after a successful test run.

## Converting a layout

To convert a single HJSON file to Zig:

```sh
zig build convert -- path/to/input.hjson path/to/output.zig
```

Or run the built executable directly:

```sh
./zig-out/bin/zkeycodes path/to/input.hjson path/to/output.zig
```

The output type is inferred from the filename: files containing `"basic"` produce a grouped keycode table; all others produce a flat alias mapping.

## Batch conversion

To convert multiple layouts at once, place all HJSON files in the `input/` directory at the project root, then run:

```sh
zig build convert-all
```

This reads every `.hjson` file from `input/` and writes the corresponding `.zig` file to `keycodes/`. The output filename is derived from the input filename by extracting the language identifier:

| Input file | Output file |
|---|---|
| `keycodes_0.0.1_basic.hjson` | `keycodes/keycodes.zig` |
| `keycodes_german_0.0.1.hjson` | `keycodes/german.zig` |
| `keycodes_us_international_0.0.1.hjson` | `keycodes/us_international.zig` |

If `input/` does not exist the step succeeds without doing anything.

After generation, import any new files in `root.zig` to make them available through the library module.

## Using as a library

Add `zkeycodes` as a dependency in your `build.zig.zon`, then import via `root.zig`:

```zig
const zkeycodes = @import("zkeycodes");

// Basic keycodes (grouped by category)
const KC_A     = zkeycodes.keycodes.basic.KC_A;
const KC_ENTER = zkeycodes.keycodes.basic.KC_ENTER;
const KC_LSFT  = zkeycodes.keycodes.modifiers.KC_LEFT_SHIFT;

// German locale layout
const DE_ADIA  = zkeycodes.ger.DE_ADIA;   // Ä
const DE_SLSH  = zkeycodes.ger.DE_SLSH;   // /  (AltGr variant)
```

Available top-level names in `root.zig`:

| Name          | Layout                  |
|---------------|-------------------------|
| `keycodes`    | Basic HID keycode table |
| `ger`         | German (DE)             |
| `ger_mac_iso` | German Mac ISO          |
| `us_intl`     | US International        |
| `dan`         | Danish                  |
| `core`        | Types and modifier fns  |

## Label lookup

Every generated file exposes a `getLabel` function:

```zig
pub fn getLabel(keycode: c_int, shortest: bool) ?[]const u8
```

- Returns the display label for a keycode value, or `null` if the value is not in the table.
- `shortest = false`: returns the label derived from the primary key name (`KC_ENTER` → `"ENTER"`).
- `shortest = true`: returns the shortest label across all names for the same value (`KC_ENTER` / `KC_ENT` → `"ENT"`).

The transparent key (`_______` = `KC_TRANSPARENT` = 0x0001) always returns `" "` (a single space) when `shortest = true`, since `_______` is shorter than `"TRANSPARENT"` or `"TRNS"`. This is useful for keyboard layout display where transparent keys should appear blank.

Labels are derived by stripping the namespace prefix up to and including the first `_` (`KC_SPACE` → `"SPACE"`, `DE_EXLM` → `"EXLM"`). Names with no underscore are returned as-is.

```zig
const keycodes = @import("zkeycodes").keycodes;

// Basic lookup
keycodes.getLabel(keycodes.basic.KC_A, false)     // → "A"
keycodes.getLabel(keycodes.basic.KC_ENTER, false)  // → "ENTER"
keycodes.getLabel(keycodes.basic.KC_ENTER, true)   // → "ENT"

// Transparent key
keycodes.getLabel(keycodes.internal._______, true) // → " "

// Unknown value
keycodes.getLabel(0x9999, false)                   // → null
```

The underlying lookup primitive is `core.getLabel`, which accepts any `[]const LabelEntry` slice, so custom label tables can be searched with the same function.

## Adding a new layout

1. Place the HJSON file in `test_data/` following the naming convention `keycodes_<lang>_<version>.hjson`.
2. Add a generation step and a dependency in `build.zig` (follow the pattern of `test_danish_cmd`).
3. Import the generated file in `root.zig`.
4. Run `zig build test` to generate the file and verify it compiles.

## Input file format

The generator handles a subset of QMK's HJSON schema. Comments, trailing commas, and unquoted keys are not supported — the files from QMK's `data/constants/keycodes/` directory work as-is.

**Basic keycodes** (`*_basic.hjson`):
```json
{
    "keycodes": {
        "0x0004": { "group": "basic", "key": "KC_A", "label": "A" },
        "0x0028": { "group": "basic", "key": "KC_ENTER", "label": "Enter", "aliases": ["KC_ENT"] }
    }
}
```

**Locale layouts**:
```json
{
    "aliases": {
        "KC_GRV":   { "key": "DE_CIRC", "label": "^ (dead)" },
        "S(DE_1)":  { "key": "DE_EXLM", "label": "!" }
    }
}
```
